Theme architecture

A theme is only a set of CSS variable overrides on [data-rdp-theme="…"] — no selectors, no component rules, no extra CSS. If a theme needs anything else, the component tokens are missing one.

/* ocean.css — the ENTIRE theme */
[data-rdp-theme="ocean"] {
  --rdp-primary: #0E7490;
  --rdp-primary-hover: #0A5B72;
  --rdp-background: #F2F7F8;
  --rdp-surface: #FFFFFF;
  --rdp-text: #123641;
  --rdp-border: #D7E3E6;
  /* …≈ 24 tokens total */
}
<!-- switching = one attribute -->
<html data-rdp-theme="ocean">
<!-- themes nest per subtree -->
<aside data-rdp-theme="dark">…</aside>
Token inheritance model
1 · Primitive tokens
Raw scales. Theme-agnostic, never used by components directly.
--rdp-green-600: #15654E
--rdp-neutral-900: #1C1B18
--rdp-space-4: 16px
→
2 · Semantic tokens
Meaning, not color. This is the layer themes override.
--rdp-primary:
  var(--rdp-green-600)
--rdp-text · --rdp-surface
→
3 · Component tokens
Per-component knobs, defaulting to semantics. Escape hatch, rarely themed.
--rdp-button-bg:
  var(--rdp-primary)
--rdp-card-radius
R1A theme file contains variables only — a linter rejects any other rule.
R2Override semantics, not components. Component tokens are for surgical exceptions.
R3Dark mode is not special — it is just a theme. No media-query forks in components.
R4Every theme must keep WCAG AA on all semantic text/surface pairs to ship as built-in.
